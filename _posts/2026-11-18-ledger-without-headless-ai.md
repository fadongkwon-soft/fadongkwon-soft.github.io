앱 수익과 후기를 한곳에 모으는 장부를 [9월에 만들었고](/ko/posts/revenue-ledger-dashboard/), [10월 초에는](/ko/posts/revenue-ledger-update/) 토스 광고 수익, 1원 프로모션, AdMob, 후기 수집을 명령 하나(`update.cmd`)로 묶었습니다. 그 뒤로 매일 이 명령 하나만 돌립니다.

그 명령의 토스 두 단계에는 처음부터 이상한 부품이 하나 들어 있었습니다. 파이썬 스크립트가 **AI 에이전트를 헤드리스 모드(`claude -p`)로 띄워서** 앱인토스 콘솔의 도구를 대신 부르게 하는 구조였습니다. 이 글은 그 부품이 어떻게 멈췄고, 왜 거기 있었고, 무엇으로 바꿨는지에 대한 기록입니다. 금액은 적지 않습니다.

## 발단 — 한도 메시지 하나에 두 단계가 같이 죽었습니다

11월 9일 새벽, 평소처럼 `update.cmd`를 돌렸더니 첫 두 단계가 이렇게 끝났습니다.

```text
[1/5] Apps in Toss - ad revenue
  ! 전체 리포트 실패 → 앱별 조회로 전환: claude -p 실패 (success): You've hit your weekly limit · resets Nov 12, 11pm
  · toss-per-app: 49건 응답 없음 → 다시 시도
toss: 앱별 조회도 모두 실패 → 잠시 후 재시도
[2/5] Apps in Toss - promotions
  · list: 3건 응답 없음 → 다시 시도
promo: 프로모션 목록을 못 받음 → 잠시 후 재시도
[3/5] AdMob - ad revenue
```

광고 수익 단계는 워크스페이스 전체 리포트가 실패하자 예비로 앱 49개를 하나씩 조회하려 했고, 그것도 전부 응답이 없었습니다. 프로모션 단계도 목록부터 못 받았습니다. 그 뒤의 AdMob과 후기 단계는 멀쩡히 돌았습니다.

저는 처음에 "weekly limit"를 **토스 쪽 API 한도**로 읽었습니다. 토스 콘솔을 부르다 난 오류이니 토스가 막은 것이라고 생각한 겁니다. 실제로는 반대였습니다. 이 메시지는 수집 스크립트가 띄운 AI 에이전트의 주간 사용 한도였고, 토스 서버에는 요청이 아예 가지 않았습니다. 상태 표시가 `(success)`인 것도 헷갈림을 키웠습니다. AI 실행 자체는 "성공"했고, 그 성공한 답변의 내용이 "한도에 걸렸다"였던 겁니다.

한도가 풀리는 날까지 토스 수익 장부는 비어 있을 수밖에 없었습니다. 수익을 모으는 스크립트가 AI 사용량에 묶여 있다는 사실을 그때 처음 정면으로 봤습니다.

## 왜 수집 스크립트가 AI를 띄웠나

토스 광고 수익과 프로모션 집행 내역은 앱인토스 콘솔 MCP 서버의 도구로만 받을 수 있습니다. 문제는 그 서버에 붙는 방법이었습니다. 공용 호출 모듈의 맨 위 주석에는 이렇게 적혀 있었습니다(제품 이름만 'AI 에이전트'로 바꿨습니다).

```python
"""공용: 헤드리스 claude 로 앱인토스 MCP 도구를 여러 번 부르고 tool_result 원본을 돌려받는다.

MCP 서버(apps-in-toss-console)는 AI 에이전트가 OAuth 로 붙는 원격 서버라 파이썬이 직접 못 부른다.
그래서 `claude -p` 에 "이 호출들을 그대로 하고 DONE 만 답하라"고 시키고, stream-json 의 tool_result 를 직접 파싱한다
"""
```

AI 에이전트에는 이 서버가 등록돼 있고 로그인도 돼 있었습니다. 그래서 "서버에 붙는 길은 AI 클라이언트뿐"이라고 여기고, 파이썬은 AI에게 "이 도구를 정확히 이 인자로 부르고 DONE만 답하라"고 시킨 뒤, AI의 출력 스트림에서 도구 응답 원본을 꺼내 쓰는 구조를 만들었습니다.

```python
prompt = (f"Call {TOOL} with exactly these arguments: {args} "
          "If the call errors or times out, call it again (at most 3 tries). "
          "Do not repeat the result. When a call succeeds, reply with just DONE.")
cmd = ['claude', '-p', '--output-format', 'stream-json', '--verbose', '--model', MODEL,
       '--max-turns', str(MAX_TURNS), '--allowedTools', TOOL]
```

돌아가기는 했습니다. 다만 몇 달 사이에 이 경로에 군살이 계속 붙었습니다.

| 붙은 군살 | 왜 필요했나 |
|---|---|
| 응답 원본을 스트림에서 직접 파싱 | AI가 50KB짜리 JSON을 받아 적으면 느리고 틀릴 수 있어서(9월) |
| 50KB 초과 응답을 파일에서 다시 읽기 | 응답이 크면 AI 쪽에서 본문 대신 "파일에 저장했다"는 안내만 남겨서(10월) |
| 빠뜨린 호출·인자를 바꾼 호출 재실행 | AI가 12건 중 일부를 안 부르거나 인자를 바꿔 부르는 일이 있어서 |
| 호출을 12건씩 나눠 3개씩 동시 실행 | 한 번에 많이 맡기면 턴 한도를 넘어서 |
| 대화 턴 한도 조정 | 정상 호출이 한도를 꽉 채워 쓰다가 시간 초과 한 번에 결과가 비어서([10월 글](/ko/posts/revenue-ledger-update/)) |
| 로그인 만료 안내 | AI 쪽 로그인이 풀리면 실패 원인이 엉뚱하게 보여서 |

모두 "AI가 중간에 있다"는 사실 하나에서 나온 처리였습니다. 그리고 이번에는 그 AI의 사용량 한도가 수집 자체를 세웠습니다.

## 추적 — 서버는 정말 AI 클라이언트만 받을까

11월 17일 새벽, AI 의존을 하나씩 줄이는 작업을 하다가 `update.cmd`를 다시 점검했습니다. AI 에이전트에게 맡겨 스크립트 전체를 훑게 한 결과는 이랬습니다.

| 단계 | 스크립트 | AI 의존 |
|---|---|---|
| 토스 광고 수익 | `toss_fetch.py` | 있음 — 헤드리스 AI로 리포트 도구 호출 |
| 토스 프로모션 | `promo_fetch.py` | 있음 — 공용 모듈로 2~3번 호출 |
| AdMob | `admob_fetch.py` | 없음 — 구글 OAuth로 직접 |
| 후기 | `play_reviews.py` | 없음 — 서비스 계정으로 직접 |
| 리포트·대시보드 | `report.py` 등 | 없음 — 로컬 파일만 |

장부 밖에서도 토스 지표(DAU·리텐션) 수집 스크립트 하나가 같은 공용 모듈을 쓰고 있었습니다.

그다음 질문은 "정말 파이썬은 못 붙는가"였습니다. MCP 서버는 인증 방식을 공개 메타데이터로 알려 줍니다. 인증 없이 읽을 수 있는 그 정보를 확인해 보니 막는 장치가 보이지 않았습니다.

| 항목 | 서버가 공개한 값 |
|---|---|
| 인증 흐름 | 표준 OAuth 인가 코드 방식 |
| 코드 보호 | PKCE 지원(S256) |
| 클라이언트 인증 | 비밀값 없는 공개 클라이언트(`none`) 허용 |
| 토큰 갱신 | refresh_token 지원 |
| 특정 클라이언트 전용 표식 | 없음. 인증 없이 부르면 표준 401만 돌아옴 |

비밀값 없는 공개 클라이언트라는 건, 데스크톱 프로그램이 브라우저 로그인 한 번으로 자기 토큰을 받을 수 있게 설계된 방식이라는 뜻입니다. AI 클라이언트도 결국 이 방식으로 붙어 있던 것이고, 파이썬이라고 다를 이유가 없었습니다.

### 토큰을 빌려 쓰려던 시도는 막혔고, 그게 맞았습니다

확인을 빨리 하려고 처음에는 **AI 클라이언트가 저장해 둔 로그인 토큰을 그대로 빌려** 파이썬으로 도구 목록을 읽어 보려 했습니다. 이 시도는 AI 에이전트의 권한 검사에서 "무단 접근"으로 분류돼 실행되지 않았습니다.

돌아보면 막히는 게 맞았습니다. 다른 프로그램이 받아 둔 자격 증명을 꺼내 쓰면, 그 프로그램의 로그인 상태와 갱신 주기에 몰래 기대는 셈이 됩니다. 한쪽이 토큰을 갱신하면 다른 쪽이 들고 있던 토큰이 무효가 되는 식으로 서로를 깨뜨릴 수도 있습니다. 그래서 방향을 바꿔 **파이썬이 자기 이름으로 따로 로그인하는 길**로 갔습니다. 사용자가 브라우저에서 한 번 로그인하면 수집기 전용 토큰 파일이 생기고, AI 클라이언트의 로그인은 건드리지 않습니다.

## 교체 — 표준 라이브러리만 쓰는 MCP 클라이언트

11월 18일 0시 무렵, 파이썬 모듈 `toss_mcp.py`를 새로 만들었습니다. 외부 패키지 없이 표준 라이브러리만 씁니다.

| 명령·기능 | 하는 일 |
|---|---|
| `login` | PKCE(S256)와 state로 인가 주소를 만들어 브라우저로 열고, 로컬 콜백으로 코드를 받아 토큰으로 바꾼 뒤 전용 파일에 저장(임시 파일에 쓰고 교체) |
| `check` | 서버 초기화 → 도구 목록 조회, 수집에 쓰는 도구 9개가 있는지 확인(읽기 전용) |
| `call` | 도구 하나를 불러 원문 출력(디버그용) |
| 토큰 관리 | 만료 60초 전에 미리 갱신, 401이 오면 한 번 갱신 뒤 재시도, 갱신까지 실패하면 "login을 다시 하라"로 멈춤 |
| 호출 | JSON-RPC 요청을 HTTP로 보내고 JSON·SSE 두 응답 형식을 모두 읽음, 세션이 만료되면 다시 초기화 |
| 일시 오류 | 연결 오류·5xx·429·시간 초과는 2초, 5초 쉬고 최대 3번 시도 |

기존 공용 모듈의 함수 이름과 반환 형태는 그대로 두고 안쪽 경로만 바꿨습니다. 그래서 프로모션 수집과 지표 수집은 코드를 거의 고치지 않고 따라왔습니다.

```python
def fetch(start, end):
    """기본은 직접 호출, LEDGER_VIA_CLAUDE=1 이면 claude -p 예비 경로. 실패하면 RuntimeError."""
    if os.environ.get('LEDGER_VIA_CLAUDE') == '1':
        return fetch_via_claude(start, end)
    return fetch_direct(start, end)


def fetch_direct(start, end):
    import toss_mcp
    args = {'workspaceId': WORKSPACE, 'request': {'startDate': start, 'endDate': end}}
    (data,), errs = toss_mcp.call_tools([('iaa_workspace_dashboard_report_v2', args)], 'toss')
    ...
```

예전 경로는 지우지 않았습니다. 환경변수 `LEDGER_VIA_CLAUDE=1`을 주면 예전처럼 헤드리스 AI로 돕니다. 직접 경로에 문제가 생겼을 때 되돌아갈 길입니다.

### 실서버 전에 가짜 서버로

토큰을 들고 실서버를 두드리기 전에, 같은 프로세스 안에 가짜 인증 서버와 가짜 MCP 서버를 띄워 테스트 17개를 만들었습니다. 로그인 코드 교환, 기본 콜백 주소, 포트가 이미 쓰이고 있을 때의 안내, 만료된 토큰의 자동 갱신과 갱신 토큰 교체, 갱신 응답에 새 갱신 토큰이 없을 때 옛 것을 유지하는지, 토큰 파일이 없거나 갱신이 실패할 때 "login을 하라"로 멈추는지, JSON과 SSE 응답 파싱, 세션 만료 뒤 재초기화, 401 뒤 갱신하고 재시도, 503 재시도, 그리고 **예전 AI 경로와 반환 형태가 똑같은지**까지 봅니다. 이 글을 쓰면서 다시 돌려 봤고, 17개 모두 11초 안에 통과했습니다.

그다음 사용자가 브라우저에서 한 번 로그인했고, `check`가 서버 접속과 도구 103개, 수집에 필요한 9개를 모두 확인했습니다. 이어서 두 단계를 실서버로 돌렸습니다.

| 단계 | 결과 | 시간 |
|---|---|---|
| 토스 광고 수익 | 17행 추가, 617행 갱신 | 1분 47초 |
| 토스 프로모션 | 프로모션 65건, 일자행 35행 추가·82행 갱신 | 15초 |

로그인 전에 확인하지 못했던 것, 즉 서버가 AI가 아닌 클라이언트도 받아 주는지, 콜백 주소가 맞는지, 동시 호출 4개가 서버 제한에 걸리는지도 이때 함께 풀렸습니다. 모두 문제없었습니다.

## 같은 날 같은 조건에서 잰 전후

교체 직후의 숫자만으로는 "얼마나 빨라졌나"를 말할 수 없었습니다. 예전 경로의 시간을 같은 조건에서 잰 적이 없었기 때문입니다. 그래서 11월 18일 밤 11시 46분부터 4분 동안, 예비 경로(`LEDGER_VIA_CLAUDE=1`)와 새 경로로 두 단계를 각각 한 번씩 돌려 PowerShell `Measure-Command`로 쟀습니다. 두 단계 모두 최근 14일을 다시 받아 덮어쓰는 정상 동작이라, 같은 장부에 몇 번 돌려도 결과는 같습니다.

| 단계 | 예전 경로(헤드리스 AI) | 새 경로(직접 호출) | 처리한 행 |
|---|---|---|---|
| 토스 광고 수익 | 123.0초 | 1.0초 | 두 번 모두 683행 갱신, 추가 0 |
| 토스 프로모션 | 80.5초 | 4.0초 | 두 번 모두 프로모션 65건, 일자행 68행 갱신 |

순서는 예전 광고 수익 → 예전 프로모션 → 새 광고 수익 → 새 프로모션이었습니다. 두 경로가 받은 데이터는 행 수까지 같았습니다.

이 표를 읽을 때 조심할 점이 하나 있습니다. 새 경로의 광고 수익 1초는 **서버 쪽 사정이 섞인 값**으로 봅니다. 토스의 워크스페이스 리포트는 평소 한 번에 1분 가까이 걸리고, 교체 직후 첫 실행도 1분 47초였습니다. 이번에는 같은 기간 같은 조회를 2분 전에 예전 경로가 먼저 보냈으니, 서버가 그 결과를 아직 들고 있었을 가능성이 큽니다. 다만 서버가 실제로 그렇게 동작하는지는 확인하지 못했습니다. 반대로 예전 경로의 123초에는 처음 조회하는 서버 시간이 들어가 있습니다.

프로모션 쪽은 해석이 더 깔끔합니다. 목록·잔액·지급 이력은 원래 빠른 조회라 서버 시간이 작고, 새 경로는 교체 직후에도 15초, 이번에는 4초였습니다. 같은 일에 예전 경로가 80초를 쓴 것은 대부분 AI 에이전트를 띄우고, 도구를 불러들이고, 호출을 나눠 맡기는 비용이라고 봅니다.

정리하면 이렇습니다. **헤드리스 AI 경로는 단계마다 수십 초의 고정 비용을 냈고, 그 비용이 사라졌습니다.** 서버가 느린 날의 광고 수익 단계는 새 경로에서도 1~2분이 걸립니다. 빨라진 것보다 더 큰 변화는 따로 있습니다. 이제 수집이 AI 사용량, AI 로그인 상태, 모델이 호출을 빠뜨리는지 같은 변수와 무관합니다.

## 부수 발견 — 자정 직후의 0원은 수집 오류가 아니었습니다

교체하고 몇 분 뒤 `update.cmd`를 전체로 돌렸더니, 최근 14일 표에서 전날(11월 17일) 토스 수익이 0으로 찍혔습니다. 바꾼 직후라 새 경로가 뭔가를 놓친 줄 알았습니다.

장부를 보니 17일 토스 행은 0원이 아니라 **행 자체가 없었습니다.** 과거 커밋 8개를 대조해 보니 토스는 늘 수집한 날의 전날까지만 들어와 있었습니다. 몇 분 뒤 서버에 같은 기간을 다시 조회하자, 17일은 앱 49개 중 19개만 행이 와 있었습니다. 15일과 16일은 49개가 다 있었습니다.

토스 광고 수익의 전날 몫은 다음 날 오전 10시 무렵까지 앱별로 순차 반영됩니다. 자정 직후에 수집하면 전날이 비어 있거나 일부만 들어오는 게 정상입니다. 수집 스크립트도 이미 이 사정을 반영해, 조회 구간의 끝을 "자료가 실제로 있는 마지막 날"로 기록합니다. 예전에 끝을 무조건 어제로 고정했다가, 아직 안 나온 날을 0원으로 적은 적이 있어서입니다.

```python
# 끝은 자료가 있는 마지막 날까지 — 토스는 어제 치를 오전 10시에 올린다(공식), 그 전엔 행이 없다.
# 예전엔 끝을 '어제'로 고정해서, 아직 안 나온 날을 0원으로 기록했다(10/15 00:25 수집의 10/14).
```

그래서 지금은 오전 10시 전의 토스 전날 수치는 확정치로 쓰지 않고, 필요하면 10시 이후에 한 번 더 돌립니다.

- **"그 길뿐"이라는 전제는 문서에 적힌 순간부터 검증되지 않습니다.** "AI 클라이언트로만 붙는다"는 주석 한 줄이 몇 달 동안 구조를 정했습니다. 서버가 공개한 인증 정보를 한 번 읽는 데는 몇 분이면 충분했습니다.
