앱인토스 워크스페이스는 앱 50개가 한도입니다. 한도가 꽉 찬 뒤로 새 허브 앱은 새로 등록하지 않고, 이미 있는 앱의 '앱 정보 변경'으로 이름·아이콘·설명을 바꾸고 번들을 허브로 갈아 끼우는 방식으로 올리고 있습니다. 그 과정은 [앱인토스 허브 전환기](/ko/posts/toss-hub-conversion/)에 적었습니다.

이번에 [파동권 주말생활](/ko/posts/hub-weekend/)도 그렇게 올렸습니다. 원래 '차번호 로또'가 있던 자리입니다. 이름과 화면은 주말생활이 됐는데, 11월 13일에 한 군데가 그대로라는 걸 알았습니다. **알림 동의창과 매일 저녁 8시 푸시가 옛 로또 앱 문구로 나가고 있었습니다.**

이 글은 그걸 찾아서 멈추고, 같은 날 다른 허브 두 곳에서 같은 문제를 고치며 밟은 함정, 그리고 앞으로 앱 정보를 바꿀 때 같이 볼 항목을 정리한 기록입니다.

## 발견: 다른 작업 중에 걸렸다

발견은 우연이었습니다. 그날 AI 에이전트 한 세션이 주말생활의 Play 출시 후속 작업(토스 주소 정리, 랜딩 페이지, 소개글)을 하다가, 토스 콘솔을 조회하던 중에 푸시 쪽 문구가 이상하다는 걸 알아챘습니다. 그 세션은 주말생활 담당이 아니어서 직접 고치지 않고, 주말생활 기획을 맡은 세션에 메시지로 넘겼습니다. 두 세션이 같은 콘솔 항목을 각자 만지면 템플릿이 중복으로 생길 수 있어서, 담당을 한 곳으로 모으는 게 맞았습니다.

넘겨받은 쪽에서 읽기 전용으로 다시 조회했고, 지적은 사실이었습니다.

| 항목 | 지금 내용 | 상태 |
|---|---|---|
| 알림 동의창 | 제목 '차번호 로또 번호 알림', 목적 '번호 뽑기', 매일 저녁 8시에 이번 주 번호를 뽑았는지 알려 준다는 내용 | 사용 중 |
| 매일 20시 푸시 | 제목 '번호 뽑기', 본문 "저녁 8시, 이번 주 번호를 뽑아요. (차번호 로또 알림)" | 승인, 매일 발송 중 |
| 푸시를 누르면 | 옛 로또 앱 주소 → 지금은 주말생활이 열림 | - |
| 허브 번들의 알림 설정 | 옛 로또 템플릿 코드를 그대로 씀 | - |

마지막 줄 때문에 상황이 더 나빴습니다. 허브 래퍼가 옛 코드를 쓰고 있으니, **주말생활에서 알림에 새로 동의한 사람도 로또 문구 동의창을 보고, 로또 문구 알림을 받는** 상태였습니다. 여행 시기와 박물관 지도를 보러 온 사람에게 저녁마다 "이번 주 번호를 뽑아요"가 가고 있었던 겁니다.

같은 앱에는 '(광고)' 로또 문구가 든 스마트 메시지도 하나 있었지만, 검수 전 상태로 한 번도 나간 적이 없어서 건드리지 않았습니다.

## 왜 남아 있었나

돌아보면 당연한 일입니다. 앱 정보 변경이 바꾸는 건 콘솔의 '앱 정보' 화면에 있는 것들, 즉 이름·아이콘·설명·스크린샷·카테고리입니다. 알림 동의문과 푸시 템플릿은 '푸시알림' 메뉴에 따로 있는 별개의 객체이고, 앱 정보를 바꿔도 전혀 따라오지 않습니다. 번들을 허브로 바꿀 때도 래퍼의 푸시 설정 파일은 예전 값을 그대로 물려받았습니다.

[9월에 기능성 푸시 시행착오](/ko/posts/toss-push-lessons/)를 정리하면서 "동의문과 템플릿은 짝"이라는 걸 배웠고, [동의 시트가 뜨지 않던 사고](/ko/posts/push-consent-root-cause/)에서는 코드 한 글자가 달라도 동의가 끊긴다는 것도 겪었습니다. 그런데 허브 전환 절차를 만들 때 이 짝을 체크리스트에 넣지 않았습니다. 규칙은 알고 있었는데, 앱의 정체가 바뀌는 순간에 그 규칙을 다시 적용할 자리가 없었던 겁니다.

## 옛 알림 멈추기: API 로는 안 됐다

선택지는 둘이었습니다. 옛 알림을 그대로 두면 새 문구가 나올 때까지 매일 로또 문구가 나갑니다. 지금 멈추면 그때까지 주말생활 동의자에게 알림이 아예 가지 않습니다. 틀린 문구를 계속 보내는 쪽이 더 나쁘다고 보고 바로 멈추기로 했습니다.

처음에는 조회 도구(MCP)의 예약 취소로 멈추려 했는데 "예약된 푸시 발송 건이 없어요"로 거부됐습니다. 이유를 보니, 매일 정기 발송은 그날 19시 35분쯤에야 그날 치 예약이 생기는 구조였습니다. 낮에는 취소할 예약 자체가 없는 겁니다. 정기 발송 자체를 멈추는 기능은 도구에 없었습니다.

그래서 콘솔 웹으로 갔습니다. 주말생활 → 푸시알림 → 해당 캠페인을 열고 '발송 중단' → 확인 창의 '중단하기'. 콘솔 로그에 '11월 13일 16시 37분 발송 중단'이 찍혔고, API 로 다시 조회해도 상태가 '중단'이었습니다. 오늘 다시 조회해도 그대로입니다. 템플릿과 동의문은 지우지 않았습니다. 지우면 되돌릴 수 없고, 나중에 기록을 대조할 근거도 사라집니다.

```text
정기 발송 템플릿 멈추기
1) API 예약 취소 → "예약된 푸시 발송 건이 없어요" (정기 발송은 당일 저녁에야 예약 생성)
2) 콘솔 웹: 푸시알림 → 캠페인 상세 → 발송 중단 → 중단하기
3) API 로 상태가 '중단'인지 다시 조회
4) 삭제는 하지 않는다
```

## 같은 날 다른 허브: 오류가 났는데 반쪽이 남아 있었다

같은 날 오후, 다른 허브인 [파동권 몬스터즈](/ko/posts/hub-monsters/)에서도 비슷한 문제를 고치고 있었습니다. 몬스터즈는 '병 돌리기'가 있던 자리를 바꾼 허브인데, 래퍼가 쓰는 허브용 템플릿 코드가 콘솔에 아예 없었고, 그 대신 병 돌리기 시절 템플릿이 월~토 저녁 8시에 "모임 순서를 병 돌리기로 정해요"로 계속 나가고 있었습니다.

새 동의문은 문제없이 만들어졌습니다. 그런데 템플릿 생성 요청이 "스마트 메시지 캠페인을 찾을 수 없습니다"라는 오류로 끝났습니다. 템플릿 목록을 여러 조건으로 다시 조회해 봤지만 새로 생긴 건 보이지 않았습니다.

여기서 바로 다시 만들지 않은 게 다행이었습니다. 템플릿은 "문구를 눈으로 확인한 뒤 한 번만 만든다"는 규칙이 있어서, 재시도 전에 콘솔 웹을 먼저 열어 봤습니다. 그랬더니 실패한 요청이 **'임시저장' 상태로 콘솔에 남아 있었습니다.** 조회 도구의 목록에는 보이지 않던 반쪽짜리였습니다. 그대로 다시 만들었다면 같은 템플릿이 두 개가 됐을 겁니다.

임시저장본을 열어 내용을 확인하고 '등록하기'를 눌렀고, AI 검수에서 바로 승인됐습니다. 다음 날 같은 작업을 여러 허브에 할 때도 생성 요청은 매번 같은 오류를 냈고, 매번 임시저장본이 남아 있었습니다. 그때 알게 된 것도 몇 가지 있습니다.

- 콘솔 목록은 처음 열었을 때 새 행이 안 보이고, 한 번 더 새로고침해야 보였습니다.
- 수정 화면 주소로 바로 들어가면 오류 화면이 떴습니다. 목록 행 클릭 → 상세의 '수정' → '등록하기' 순서로만 됐습니다.
- 조회 도구도 이름으로 검색하면 임시저장본이 보였습니다. 기본 목록 조회에만 빠져 있었던 겁니다.

## 템플릿 코드에는 옛 앱 이름이 강제로 붙는다

몬스터즈 템플릿을 만들 때 하나가 더 걸렸습니다. 래퍼에는 허브 이름을 딴 코드가 적혀 있었는데, 토스는 템플릿 코드 앞에 **앱의 내부 이름(appName)을 접두어로 강제로** 붙입니다. 그리고 appName 은 앱 정보 변경으로도 바뀌지 않습니다. 몬스터즈의 appName 은 여전히 병 돌리기 시절의 것이라, 허브 이름으로 시작하는 코드는 만들 수가 없었습니다.

```text
래퍼에 적혀 있던 코드   hub-monsters-DAILY_18B        ← 만들 수 없음
실제로 만든 코드        <옛 앱의 appName>-DAILY_18    ← 접두어 강제
```

그래서 템플릿은 옛 앱 이름으로 시작하는 코드로 만들고, 래퍼 쪽 코드를 그 값에 맞췄습니다. 주말생활의 토스 주소가 지금도 옛 로또 앱 이름으로 된 것과 같은 구조입니다. 사용자에게 보이는 문구는 바꿀 수 있지만, 코드와 주소에는 옛 앱 이름이 영구히 남습니다. 혼동을 줄이려면 문서에 "이 허브의 appName 은 옛 앱의 것"이라고 한 줄 적어 두는 수밖에 없습니다.

## 승인된 문구는 고칠 수 없고, 동의문과 맞아야 한다

다음 날에는 [파동권 올림픽](/ko/posts/hub-sports/)이 같은 상태라는 걸 확인했습니다. 픽셀 탁구 자리였던 허브인데, 매일 20시에 "저녁 8시, 오늘의 탁구 대결 시간이에요. (픽셀 탁구 알림)"이 나가고 있었습니다. 여기서 두 가지를 더 배웠습니다.

1. **승인된 템플릿은 수정할 수 없습니다.** 문구만 바꾸려 하자 "이미 승인된 메시지는 수정할 수 없어요"로 거부됐습니다.
2. **새 템플릿은 동의문과 맥락이 맞아야 통과합니다.** 같은 동의문 아래에 올림픽 문구로 새 템플릿을 만들려 하자 AI 검수에서 반려됐습니다. 사유는 동의문은 탁구 대결 안내인데 내용은 올림픽 종목 전체라는 것이었습니다.

결국 고치는 길은 두 갈래로 정리됐습니다.

| 길 | 언제 | 하는 일 | 옛 동의자 |
|---|---|---|---|
| A. 같은 동의문, 새 템플릿 | 동의문 문구가 일반적일 때(예: '두뇌 훈련 알림') | 새 템플릿만 만들고 승인되면 옛 템플릿 중단. 번들 교체 불필요 | 그대로 받는다 |
| B. 새 동의문, 새 템플릿, 번들 교체 | 동의문이 옛 앱에 묶여 있을 때(예: '탁구 대결 알림', '로또 번호 알림') | 새 동의문 + 새 템플릿 + 래퍼 코드 변경 + 번들 재배포, 라이브 뒤 옛 템플릿 중단 | **새 동의문으로 자동 이전되지 않는다. 다시 동의받아야 한다** |

다음 날 나머지 허브들을 점검했을 때, 동의문이 일반적인 곳은 A 로 통과했고 옛 앱에 묶인 곳은 B 로 갔습니다. 덧붙이면, 템플릿 본문 끝에 붙는 '(○○ 알림)'은 템플릿을 만들 때의 앱 제목으로 굳습니다. 새 템플릿을 만들면 지금의 허브 제목으로 바뀌니, A 만으로도 옛 앱 이름이 사용자 눈에서 사라집니다. 한 번은 "저녁 7시" 같은 시각이 본문에 없다는 이유로 발송 시점 반려가 났고, 본문에 시각을 넣자 통과했습니다.

주말생활은 동의문 제목부터 '차번호 로또 번호 알림'이라 B 입니다. 순서는 이렇게 잡았습니다.

1. 주말생활 문구의 새 동의문과 새 매일 알림을 하나씩, 문구를 눈으로 확인한 뒤 한 번만 만듭니다.
2. 래퍼가 새 코드를 쓰게 바꿔 번들을 올립니다.
3. 새 번들이 라이브되면 옛 알림을 비활성화합니다(이미 멈춰 둔 상태). 삭제는 하지 않습니다.
4. 옛 동의자는 새 동의창에서 다시 동의해야 받습니다.

이 글을 쓰는 시점에 주말생활의 새 동의문과 템플릿은 아직 만들지 않았습니다. 주말생활 수록 앱을 바꾸는 작업과 묶어서 할 예정이라, 그때까지 주말생활 동의자에게는 알림이 나가지 않습니다. 앱 정보 검토는 한 번 제출하면 취소할 수 없어서, 앱 정보와 푸시 교체를 한 회차에 모아 내기로 했습니다. 다음 허브 후보(옛 '내 이름 로또' 자리)도 같은 문제가 있을 게 뻔해서, 같은 순서를 그 계획에 미리 넣었습니다.

## 체크리스트: 앱 정보 변경 때 같이 볼 것

이번에 걸린 것과 그 전 허브 전환에서 걸린 것을 합쳐 표로 만들었습니다. 대부분은 '앱 정보 변경'이 바꾸지 않는 것들입니다.

| 항목 | 따라 바뀌나 | 확인할 것 | 고치는 곳 |
|---|---|---|---|
| 이름·아이콘·설명·스크린샷 | 바뀐다(앱 정보 변경 대상) | 한 번에 모아 제출(검토 취소 불가) | 콘솔 앱 정보 |
| 내부 앱 이름(appName)·토스 주소 | **안 바뀐다(영구)** | 공유 링크·QR·문서의 주소를 옛 이름 기준으로 맞춘다 | registry·사이트 |
| 연령 등급 | 안 바뀐다 | 옛 앱 등급(예: 19세 이상)이 허브에 그대로 남는다 | 바꿀 수 없음 |
| 알림 동의문 | **안 바뀐다** | 제목·목적이 옛 앱 문구인가 | 콘솔 푸시알림(새로 만들기) |
| 정기 푸시 템플릿 | **안 바뀐다** | 지금 발송 중인 문구, 본문 끝 '(옛 앱 이름 알림)' | 새 템플릿, 옛 것은 중단 |
| 래퍼의 푸시 코드 | 안 바뀐다 | 콘솔에 실제로 있는 코드인가, 접두어가 appName 인가 | 래퍼 설정 + 번들 |
| 미발송 스마트 메시지·광고성 초안 | 안 바뀐다 | 옛 문구 초안이 검수에 올라가 있지 않은가 | 콘솔(그대로 두거나 정리) |
| 생성 오류가 난 템플릿 | - | 콘솔 웹에 임시저장본이 남았는가(목록 새로고침) | 임시저장본을 마저 등록 |
| 혜택탭 프로모션 | 안 바뀐다 | 옛 앱 프로모션 문구·미션이 허브와 맞는가. 종료는 되돌릴 수 없다 | 콘솔 프로모션 |
| 광고 지면 보상 문구 | 안 바뀐다 | 보상 단위가 옛 앱 말(예: '번호')로 되어 있지 않은가 | 지면 설정 |
| 대표 전환 지표 | 안 바뀐다 | 광고 없는 허브인데 '광고 시청'이 대표 지표로 남아 있지 않은가 | 콘솔 핵심 지표 |
| 카테고리 | 앱 정보로 바뀐다 | 같은 회차에 골랐는가 | 콘솔 앱 정보 |

몬스터즈의 대표 전환 지표는 실제로 광고가 없는 앱인데 '인앱 광고 시청'으로 남아 있어서, 같은 날 '알림 동의'로 바꿨습니다. 이것도 앱 정보 변경이 건드리지 않는 항목이었습니다.

## 배운 것

- **'앱 정보 변경'은 앱의 정체성 전부가 아닙니다.** 사용자가 보는 문구는 앱 정보, 푸시, 프로모션, 광고 지면에 흩어져 있고 콘솔 메뉴도 제각각입니다. 앱의 정체가 바뀌면 메뉴마다 한 번씩 열어 봐야 합니다.
- **도구가 실패라고 해도 콘솔을 먼저 봅니다.** 생성 요청이 오류를 내도 반쪽이 남아 있을 수 있습니다. 한 번만 만들어야 하는 객체는 재시도 전에 화면에서 확인합니다.
- **동의는 옮겨지지 않습니다.** 동의문을 새로 만들면 옛 동의자는 새 동의자가 아닙니다. 그래서 옛 템플릿을 언제 멈출지는 새 번들이 라이브된 뒤에 정합니다.
- **영구히 남는 이름은 문서에 남깁니다.** appName 과 템플릿 접두어는 바꿀 수 없으니, 허브마다 "이 앱의 내부 이름은 옛 ○○"를 적어 두면 다음 사람(다음의 저)이 덜 헤맵니다.
- **다른 작업 중에 발견한 문제는 담당에게 넘깁니다.** 이번에도 발견한 세션이 직접 고쳤다면 템플릿이 두 번 만들어졌을 수 있습니다.

푸시 조회와 콘솔 작업은 AI 에이전트와 함께 했고, 알림을 멈출지와 어느 길로 고칠지는 제가 정했습니다.
