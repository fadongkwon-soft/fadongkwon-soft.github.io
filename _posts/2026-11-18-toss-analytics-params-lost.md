10월 말, [탭 버드가 앱인토스 파트너 성장 프로그램에 뽑혔고](/ko/posts/toss-growth-program-tap-bird/), 토스가 10월 26일부터 '미니앱 10초 구경하고 포인트 받기' 프로모션으로 사람을 보내 주기 시작했습니다. 그 글 끝에 "재방문은 `?from=growth` 코호트로 따로 잰다"고 적었습니다. 콘솔의 프로모션 진입 경로에 `?from=growth`를 붙이고, 앱이 이 값을 읽어 진입 이벤트를 남기게 한 것입니다.

```ts
if (GROWTH_ENTRY) logEvent('tb_growth_enter', {});
```

이 글은 그 측정이 왜 처음 며칠 동안 거의 쓸모가 없었는지에 대한 기록입니다. 원인은 프로그램이 아니라 제 래퍼 코드 한 줄이었고, 그 한 줄은 9월 중순부터 6주 동안 아무 오류도 내지 않았습니다.

## 발단 — 진입 55건, 화면 1,070건

10월 27일 저녁, 탭 버드의 진입 이벤트를 콘솔 이벤트 로그 API로 조회했습니다.

| 이벤트 | 10/26 | 10/27(조회 시점까지) | 콘솔이 보여 준 파라미터 |
|---|---|---|---|
| `tb_growth_enter`(성장 유입 진입) | 55 | 59 | `anonymous_key`, `is_private_mode` |
| `tb_run_start`(판 시작) | 17 | 9 | `anonymous_key`, `is_private_mode` |

같은 날 하루 사용자는 754명이었습니다. 판 시작 이벤트 17건은 그에 비해 터무니없이 적었습니다. 그런데 이때 처음 내린 판단은 "콘솔 이벤트 숫자는 원래 사용자 수보다 훨씬 적게 잡히니, 전체 인원이 아니라 흐름 비교용으로만 보자"였습니다. 근거 없는 가정이었습니다.

다시 처음부터 확인하자는 요청을 받고, 비교 대상을 하나 더 꺼냈습니다. 토스 SDK가 스스로 남기는 화면 로그 `/::screen`입니다.

| 이벤트 | 10/24 | 10/25 | 10/26 |
|---|---|---|---|
| `/::screen`(SDK가 남기는 화면 로그) | 71 | 53 | 1,070 |
| `tb_growth_enter`(우리가 남기는 진입 로그) | — | — | 55 |

프로그램 시작일에 화면 로그는 평소의 스무 배로 뛰었습니다. 진입 경로는 10월 24일에 이미 `?from=growth`로 바뀌어 있었으니, 이날 들어온 사람은 대부분 성장 유입입니다. 정상이라면 진입 이벤트가 화면 로그와 비슷한 크기여야 합니다. 55건은 20분의 1이었습니다.

또 하나 이상한 점이 있었습니다. 판 시작 이벤트는 모드·월드·스테이지·새 종류를 같이 넘기는데, 콘솔에 보이는 파라미터는 SDK가 자동으로 붙이는 두 개뿐이었습니다. **우리가 넣은 값이 하나도 없었습니다.**

## 추적 — 래퍼가 SDK에 넘기던 모양

### 앱 쪽은 한 줄짜리 전달이었습니다

게임 모노레포의 공용 패키지는 분석 로그를 이렇게 넘깁니다. 토스에서만 전송되고 Play와 웹에서는 아무것도 안 하는 얇은 함수입니다.

```ts
export function logEvent(name: string, params: Record<string, LogValue> = {}): void {
  try {
    window.TossAdsBridge?.logEvent?.(name, params);
  } catch {
    /* 분석 로그 실패는 무시 */
  }
}
```

실제 전송은 토스용 래퍼마다 들어 있는 브릿지(`toss-bridge.js`)가 합니다. 문제는 여기였습니다.

```js
// 바꾸기 전
logEvent(name, params) {
  try {
    const fn = Analytics?.log;
    if (typeof fn !== 'function') return;
    const p = fn({ log_name: name, ...(params || {}) });
    if (p && typeof p.catch === 'function') p.catch(() => {});
  } catch {
    /* 분석 로그 실패는 게임을 막지 않는다 */
  }
},
```

이벤트 이름과 값을 한 객체에 **펼쳐서** 넘깁니다. `{ log_name: 'tb_run_start', mode: 'adventure', world: 2, ... }` 같은 모양입니다.

### SDK 계약은 타입 정의와 소스에 있었습니다

추측 대신 래퍼에 설치된 SDK(`@apps-in-toss/web-framework` 3.5.0)의 타입 정의를 열었습니다.

```ts
interface EventLogParams$1 {
  log_name: string;
  log_type: string;
  params: Record<string, LogParam>;
}

interface EventLogParams extends Omit<EventLogParams$1, "log_type"> {
  log_type: "debug" | "info" | "warn" | "error" | "event" | "screen" | "impression" | "click" | "popup";
}

declare const Analytics: {
  log: (params: EventLogParams) => Promise<void>;
  ...
};
```

계약은 `{ log_name, log_type, params: {...} }`입니다. 값은 `params` 안에 묶여야 하고 `log_type`이 있어야 합니다. 같은 패키지의 실행 코드를 보면 `Analytics.log`는 받은 객체를 그대로 토스 앱의 네이티브 쪽으로 넘깁니다.

```js
const eventLog = (params) => callAsyncMethod("eventLog", params);
...
const Analytics = {
  log: eventLog,
  ...
};
```

SDK가 스스로 남기는 클릭·노출·화면 로그도 모두 이 모양으로 만들어 보냅니다.

```js
return eventLog({
  log_type: "event",
  log_name: log_name ?? `${groupId}::click`,
  params: { ...otherParams, search, referrer: getReferrer(), ... }
});
```

정리하면 이렇습니다.

| | 우리 래퍼가 보낸 것 | SDK 계약 |
|---|---|---|
| 이벤트 이름 | `log_name` | `log_name` |
| 이벤트 종류 | 없음 | `log_type: 'event'` |
| 커스텀 값 | 최상위에 펼침 | `params` 객체 안 |

SDK는 이 객체를 검사하지 않고 넘기고, 네이티브 쪽은 `params`가 없으니 기본 파라미터만 붙여 기록했습니다. 커스텀 값이 전부 사라진 이유는 이것으로 설명됩니다. 이벤트가 왜 대부분은 빠지고 일부만 남았는지는 토스 쪽 처리를 볼 수 없어서 확인하지 못했습니다.

### 같은 코드가 몇 개나 있었나

래퍼 폴더를 전부 훑었습니다.

| 브릿지 상태 | 래퍼 수 |
|---|---|
| logEvent가 있고 잘못된 형식(값 펼침) | 25 |
| logEvent 자체가 없음(앱이 불러도 아무것도 안 남음) | 43 |

잘못된 형식은 9월 17일 "토스 브릿지 29개에 logEvent 통일" 커밋에서 처음 들어갔고, 그 뒤 새 래퍼는 이 브릿지를 복사해 만들어 같은 줄을 물려받았습니다. logEvent가 없는 43개는 앱 코드의 `window.TossAdsBridge?.logEvent?.(...)`가 조용히 아무것도 하지 않았습니다. 두 경우 모두 화면에도 콘솔에도 오류는 한 줄도 없었습니다. `Analytics.log`는 미지원 앱 버전에서도 "에러 없이 조용히 무시"되게 만들어진 API이고, 래퍼는 그 위에 try/catch와 `.catch(() => {})`까지 씌워 두었습니다.

## 수익에 영향이 있었나 — 범위를 먼저 정했습니다

고치는 것 자체는 한 줄이지만, 고칠 때마다 번들을 새로 빌드하고 검수를 받아야 합니다. 그래서 먼저 "광고 수익이나 앱 동작에 영향이 있는가"를 코드로 확인했습니다.

- 광고 표시, 하트(보상형 광고로 채우는 기회), 1원 프로모션 지급은 모두 logEvent를 쓰지 않습니다. logEvent를 부르는 곳은 판 시작·끝, 모드별 기록, 리더보드 열기, 크로스 프로모션 노출·클릭 같은 분석용 이벤트뿐이었습니다.
- logEvent는 앱 쪽과 브릿지 쪽 모두 try/catch로 감싸져 있어, 실패해도 게임 흐름을 막지 않습니다.

영향은 분석에만 있다는 결론이었고, 그래서 **성장 프로그램 측정에 직접 쓰는 두 앱(탭 버드·오목)만 먼저 고쳐 배포**하고, 나머지 23개는 소스만 고쳐 각 앱의 다음 빌드에 실리게 했습니다.

```js
// 바꾼 뒤
logEvent(name, params) {
  try {
    const fn = Analytics?.log;
    if (typeof fn !== 'function') return;
    // SDK 계약 { log_name, log_type, params } — 값을 펼쳐 넣으면 params 가 사라지고 대부분 누락된다(10/27 발견).
    const p = fn({ log_name: name, log_type: 'event', params: params || {} });
    if (p && typeof p.catch === 'function') p.catch(() => {});
  } catch {
    /* 분석 로그 실패는 게임을 막지 않는다 */
  }
},
```

| 시각(10/27) | 한 일 |
|---|---|
| 18:46 | 탭 버드·오목 브릿지 수정 커밋 |
| 18:51 | 나머지 래퍼 23개 브릿지 수정 커밋(검수 요청 없음) |
| 그 직후 | 탭 버드 20261027-45, 오목 20261027-32 테스트 번들을 폰으로 보내 확인한 뒤 검수 요청 |

두 번들은 다음 날 저녁 확인했을 때 이미 승인·출시돼 라이브였습니다.

## 결론 — 고친 뒤의 숫자

10월 30일 오후에 같은 API로 다시 조회했습니다.

| 날짜 | `/::screen` | `tb_growth_enter` | `tb_run_start` |
|---|---|---|---|
| 10/26 | 1,070 | 55 | 17 |
| 10/27 | 1,616 | 380 | 64 |
| 10/28 | 1,788 | 1,224 | 448 |
| 10/29 | 1,739 | 1,157 | 1,599 |

진입 이벤트가 하루 약 1,200건으로 올라와 화면 로그(약 1,700건)와 같은 자릿수가 됐습니다. 더 직접적인 증거는 파라미터 목록입니다. 판 시작 이벤트의 파라미터가 `anonymous_key`, `is_private_mode` 두 개에서 `mode`, `kind`, `world`, `stage`, `bird`, `growth`까지 늘었습니다. 넣은 값이 비로소 도착한 겁니다.

숫자를 해석할 때 주의할 점이 둘 있습니다.

- 10월 28일 밤에는 탭 버드의 다음 번들(성장 유입이면 홈을 건너뛰고 바로 첫 비행, 진입 판별 보강)도 출시됐습니다. 그래서 10월 29일 판 시작 수의 급증에는 화면 흐름 변경의 효과가 섞여 있습니다. 진입 이벤트가 10월 28일에 이미 1,224건이었던 것은 그 번들이 나가기 전이라, 형식 수정의 효과로 봅니다.
- 진입 이벤트와 화면 로그가 같은 숫자일 필요는 없습니다. 한 사람이 여러 화면을 보면 화면 로그가 더 많이 쌓입니다. 중요한 건 20분의 1이던 비율이 같은 자릿수로 돌아왔다는 점입니다.

그리고 고치기 전 6주 동안의 커스텀 값은 되살릴 수 없습니다. 탭 버드·오목의 성장 프로그램 첫 이틀 측정(첫 판 시작률 등)은 이 버그 때문에 판단에 쓸 수 없었습니다.

## 남은 것

- **나머지 래퍼의 라이브 반영**: 23개는 소스만 고쳤고, 각 앱이 다음에 빌드·출시될 때 반영됩니다. 지금 소스 기준으로는 logEvent가 있는 래퍼 27개(그 뒤 새로 만들거나 logEvent를 넣은 2개 포함)가 모두 올바른 형식입니다. 다만 모든 앱의 라이브 번들에 실제로 반영됐는지는 하나하나 확인하지 않았습니다.
- **logEvent가 없는 래퍼**: 지금 기준 47개는 여전히 함수가 없어, 그 앱들의 분석 이벤트는 남지 않습니다. 분석이 필요한 앱부터 넣을 생각입니다.
- **자동 검사**: 이 사고는 [출시 사고 연대기](/ko/posts/launch-incidents/)에서 "아직 자동 검사가 없는 유일한 항목"으로 적었습니다. 지금은 화면 로그 대비 커스텀 이벤트 비율과 파라미터 목록을 손으로 봅니다. 브릿지 소스에서 `log_type`과 `params` 묶음을 확인하는 검사를 출시 게이트에 넣는 것이 다음 일입니다.

## 배운 것

- **오류 없이 받아 주는 로그 API는 형식이 틀려도 조용합니다.** 분석 로그는 게임을 막으면 안 되니 실패를 삼키게 만드는 게 맞습니다. 그 대가로 "틀렸다"는 신호도 같이 사라집니다. 이런 API는 호출이 성공했다는 사실로는 아무것도 증명되지 않습니다.
- **"원래 적게 잡힌다"고 넘기지 말고 독립된 수치와 대조합니다.** 같은 앱, 같은 날, 같은 사람들에 대해 다른 경로로 쌓이는 숫자(여기서는 SDK가 스스로 남기는 화면 로그)를 옆에 놓으면 20분의 1이라는 어긋남이 바로 보입니다.
- **값이 도착했는지는 파라미터 목록으로 확인합니다.** 이벤트 수만 보면 일부가 남아 있어 "동작은 한다"고 착각하기 쉽습니다. 콘솔이 보여 주는 파라미터 이름에 내가 넣은 키가 있는지가 더 확실한 증거였습니다.
- **계약은 문서 대신 설치된 SDK의 타입 정의와 소스에서 확인합니다.** 몇 분이면 열어 볼 수 있고, 내 래퍼가 SDK 자체 코드와 같은 모양으로 부르는지 바로 비교할 수 있습니다.
- **복사로 퍼진 코드는 고칠 때도 전부 찾습니다.** 한 줄이 25개 래퍼에 똑같이 들어 있었습니다. 고칠 범위는 영향(수익이냐 분석이냐)으로 나누되, 소스는 한 번에 고쳐 다음 빌드부터는 다시 퍼지지 않게 했습니다.
